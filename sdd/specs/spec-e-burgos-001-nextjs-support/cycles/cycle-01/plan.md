# spec-e-burgos-001-nextjs-support — cycle-01 · plan (lite)

> Módulo: nextjs-support | Subproyectos: libs/tucu-ui, tools/mcp-server, apps/next-demo | Fecha: 2026-10-26
> Objetivo: que `@e-burgos/tucu-ui` funcione en Next.js 16 (App Router, incluido `output: 'export'`) mediante un entry desacoplado `@e-burgos/tucu-ui/next`, sin que ninguna app Vite que usa 3.x cambie una línea. Fuera de alcance: Pages Router, Server Components propios de la librería, Module Federation, migrar Studio (sdd-harness) a tucu-ui.

## Historias
- US-001 — Como dev con una app Vite en tucu-ui 3.x quiero actualizar a 3.4.0 sin tocar código para no pagar la llegada de Next. CA: las suites existentes de `ui/tucu-ui` pasan sin modificarse; `apps/demo`, `apps/test-lib` y `examples/standalone` compilan y navegan igual.
- US-002 — Como dev con Next 16 quiero envolver mi `app/layout.tsx` con `NextThemeProvider` para usar layouts, menús y links de tucu-ui con el ruteo de Next. CA: la app de prueba navega entre páginas con `next/link`, el menú marca la ruta activa y no se monta ningún router de react-router.
- US-003 — Como dev con Next 16 quiero importar componentes de tucu-ui desde páginas Server Component sin escribir `"use client"` a mano. CA: `next build` con `output: 'export'` termina sin errores de client boundary.
- US-004 — Como agente de front quiero que el MCP genere código para Next cuando el proyecto es Next. CA: `generate_page`/`generate_component` con `framework: "next"` emiten `NextThemeProvider`/`next/link`; sin el parámetro emiten lo mismo que 0.9.0.

## Tasks (detalle en tasks.json)
- TASK-001 — Capa de navegación interna en `ui/tucu-ui/src/themes/navigation/`: contexto `TucuNavigation` (pathname, search params, params, `navigate(to, { replace })`, componente `Link`) y hook `useTucuNavigation`. Sin provider de tucu en el árbol, el hook detecta el Router del ancestro con `useInRouterContext()` y usa los hooks de react-router, así que las apps que montan su propio `BrowserRouter` sin `ThemeProvider` se comportan exactamente como en 3.3. Migrar a esa capa los 27 módulos de `src/` (sin contar tests) que hoy importan `react-router-dom`: layouts, menús, links, tabs por parámetro, macOS, docs-kit y hooks. El alias `src/react-router-dom` queda solo como re-export público. `BrowserRouter`/`Routes` siguen solo en los providers Vite. Valida: suites existentes sin cambios + tests nuevos de la capa con y sin provider.
- TASK-002 — `"use client"` y SSR: marcar los módulos con estado, efectos, contexto o APIs del navegador y hacer que el build ESM (`preserveModules`) conserve la directiva por módulo; el bundle CJS raíz no la lleva. Auditar y corregir los accesos a `window`, `document`, `localStorage` y `matchMedia` durante el render (incluido el store de tema con zustand y su hidratación) para que el prerender del servidor no falle ni produzca diferencias de hidratación. Valida: script de verificación sobre `dist/` que falla si un módulo cliente perdió la directiva; el build de Vite de `apps/demo` sigue sin warnings nuevos.
- TASK-003 — Entry `./next`: `NextThemeProvider` arma el adaptador con `usePathname`/`useRouter`/`useSearchParams`/`useParams` de `next/navigation` y `next/link`, y monta `ThemeWrapper` con `children` (las páginas de Next) en lugar de `BrowserRouter` + rutas. Segundo entry en el build de Vite, solo ESM, `exports["./next"]` en `package.json`, `next` como peer dependency opcional (`>=16`), ningún import de `next` alcanzable desde el barrel raíz y ningún import de `react-router-dom` alcanzable desde `./next`. El adaptador normaliza `usePathname()` (quita `basePath` y la barra final) para que la ruta activa compare igual que con react-router, y su `Link` acepta URLs externas, `target` y `prefetch`. Valida: tests con `next/navigation` mockeado + chequeo de que `dist/index.*` no referencia `next`.
- TASK-004 — App de prueba `apps/next-demo` (privada, en el workspace): Next 16.4 App Router, `output: 'export'`, Tailwind v4 con `@e-burgos/tucu-ui/theme` + `@source`, `NextThemeProvider` en `app/layout.tsx`, y al menos `AdminLayout`, un formulario, una `DataTable` y un chart. Las páginas son Server Components finos que importan secciones cliente propias, porque las columnas y callbacks son funciones; la API pública de los componentes no cambia. Targets Nx `build` y `lint`. Valida: `nx build next-demo` genera `out/` y un e2e mínimo navega entre dos páginas con el menú activo correcto.
- TASK-005 — MCP en modo Next: parámetro opcional `framework: "vite" | "next"` (default `vite`) en las tools generadoras, resources `quickstart`, `routing` y `shell` con la sección Next, y prompt `theme-setup` que pregunta el framework. Valida: tests del MCP; los snapshots de salida en modo `vite` no cambian.
- TASK-006 — Documentación y release: README (es/en) y docs site con la guía de Next, CHANGELOG de ambos paquetes, `@e-burgos/tucu-ui` 3.4.0 y `@e-burgos/tucu-ui-mcp` 0.10.0. Valida: `nx run-many -t lint test build` en verde y `examples/standalone` construido contra el paquete empaquetado (`pnpm pack`).

## Decisiones técnicas
- Adaptador de navegación propio en lugar de depender de react-router en Next → desacopla los componentes del router concreto y deja a cada provider llenar el mismo contrato → afecta `components.json` (nuevos `TucuNavigation`, `NextThemeProvider`) bajo `libs/tucu-ui`.
- Entry separado `@e-burgos/tucu-ui/next` en vez de un prop en `ThemeProvider` → una app Vite nunca carga `next` y una app Next nunca monta `BrowserRouter`; el barrel raíz queda idéntico.
- El namespace público `ReactRouter` y el `ThemeProvider` actual se mantienen tal cual → compatibilidad 3.x (la eliminación, si llega, es tema de una v4).
- Next 16 como piso de la peer dependency (`>=16`) y 16.4.3 (última estable en npm al 2026-10-26) fijada en la app de prueba; solo App Router.
- Release como minor (3.4.0) porque no hay cambios incompatibles. El barrel raíz solo suma exports (`useTucuNavigation` y sus tipos); nada se quita ni se renombra.
- `ThemeWrapper` es la frontera: lo comparten ambos providers; el auth/redirect a login en Next queda en la app (middleware de Next), no en la librería.
